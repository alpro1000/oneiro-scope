**Новое в сессии 2026-07-27 part 5 (OAuth discovery, ветка перезапущена с main):**
- **Issuer публиковался нормализованным.** `protected_resource_metadata()`
  отдавал `MCP_AUTH_ISSUER.rstrip("/")`. Тонкость: `rstrip("/")` встречается в
  `remote.py` трижды и дважды он **правильный** — в `jwks_url()` перед
  well-known путём и при валидации токена, где обрезаются обе стороны (именно
  это не даёт отклонить живой Auth0-токен из-за слэша). Третий случай другой по
  природе: это issuer-**идентификатор**, отданный клиенту, который по RFC 8414
  §3.3 построит из него URL метаданных и потребует, чтобы вернувшийся `issuer`
  совпал посимвольно. Auth0 отдаёт со слэшем → строгий клиент вправе прервать
  флоу. Теперь публикуется дословно.
- **Метаданные отдавались только по «голому» пути.** RFC 9728 §3.1 вставляет
  `/.well-known/oauth-protected-resource` **между хостом и путём** идентификатора
  ресурса: для `https://host/mcp` документ живёт по
  `.../oauth-protected-resource/mcp`. Голый путь корректен только для ресурса
  без пути. Теперь отдаются оба, канонический первым, и `WWW-Authenticate`
  указывает на канонический.
- **Почему это так хорошо спряталось:** Claude подключается нормально, потому
  что буквально идёт по `WWW-Authenticate` и попадает на тот путь, который мы
  случайно и отдавали. Работающий клиент подтвердил не то: он проверял путь из
  заголовка, а не построенный по RFC, и не сверял строки issuer.
- Валидация токена намеренно не тронута; `test_issuer_trailing_slash_is_tolerated`
  проходит — терпимость при *сравнении* верна, нормализация при *публикации* нет.
- Проверено сквозь ASGI-приложение с настройками живого деплоя: оба пути 200,
  `authorization_servers` со слэшем, заголовок на канонический путь.
