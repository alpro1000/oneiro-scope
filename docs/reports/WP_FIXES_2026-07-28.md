## WP-6 — Блок версионирования в каждом ответе ✅

**Что изменилось.** Новый модуль `backend/mcp/tools/_meta.py`: обёртка
`with_meta` (sync и async), которая добавляет в каждый ответ инструмента блок

```json
"meta": {
  "server_version": "1.5.0", "commit": "<git sha|RENDER_GIT_COMMIT|untracked>",
  "schema_version": "2", "request_id": "req_…", "input_hash": "sha256:…",
  "duration_ms": 12, "cache_hit": false, "computed_at": "…+00:00"
}
```

Все регистрации в `backend/mcp/server.py` переведены на
`mcp.tool()(with_meta(fn))` — обойти обёртку нельзя без правки server.py.
`input_hash` считается от связанных (bound) аргументов вызова — одинаковый
вход даёт одинаковый хэш, разный — разный. `computed_at` всегда tz-aware.

**Тесты.** `backend/tests/test_response_meta.py`:
- AST-проверка: каждая регистрация обёрнута `with_meta` (структурный страж);
- runtime: sync- и async-инструменты реально возвращают все 8 полей;
- стабильность `input_hash` (два одинаковых вызова → одинаковый хэш,
  другой вход → другой хэш; `request_id` при этом различается);
- tz-awareness таймстампов ответа dreams.

**Критерии приёмки.** Выполнены: блок присутствует во всех ответах (47/47
инструментов через одну точку), commit берётся из RENDER_GIT_COMMIT/git.
`cache_hit` пока константно `false` — честно: серверного кэша ответов на
MCP-пути сейчас нет; поле станет информативным, если кэш появится.

## WP-2 — Дома в calculate_natal_chart ✅

**Корневая причина.** `NatalChartCalculator.assign_planets_to_houses`
существовал, но **ни одна строка кода его не вызывала**: сервис считал
куспиды и тут же отдавал ответ, где у каждой планеты `house: null`, а у
каждого дома `planets: []`. money_contour/vocation_map считают дома своим
кодом — отсюда расхождение из аудита.

**Что изменилось.**
1. `service.calculate_natal_chart` теперь вызывает привязку планет к домам
   (когда есть время рождения) — заполняются **обе стороны** связи:
   `planet.house` и `houses[i].planets`.
2. `House.cusp_degree` — абсолютная эклиптическая долгота куспида (0–360)
   в контракте; раньше куспид был восстановим только из sign+degree.
3. `planet.house_borderline` + `planet.distance_to_cusp_deg`: расстояние до
   ближайшего из двух куспидов своего дома; < 1° → borderline (минуты
   ошибки времени рождения смещают дом).
4. Тихий фолбэк Placidus→WholeSign при исключении **удалён** (провенанс
   обещает Placidus — подмена системы домов без объявления это §12);
   сбой `swe.houses` теперь RuntimeError. Заодно удалена ветка
   `_swe is None` (после WP-1 недостижима).
5. Без времени рождения — честный null всех трёх полей (без изменений,
   покрыто тестом).

## WP-3 — applying/separating по реальным скоростям ✅

**Корневая причина.** `_is_applying` был эвристикой по классам планет с
финальным `return True  # for simplicity` — отсюда «все 20 аспектов
applying:true» в живом прогоне аудита. Скорости эфемерида считал и
выбрасывал (оставался только флаг retrograde).

**Что изменилось.**
1. `PlanetPosition.speed_deg_per_day` — скорость из эфемерид теперь в
   контракте (южный узел — та же скорость, что северный: антипод).
2. `_find_aspect`: знаковое разделение s ∈ (−180, 180], отклонение
   deviation = |s| − exact; аспект applying ⇔ |deviation| убывает ⇔
   `deviation · d|s|/dt < 0`, где d|s|/dt = ±(v₁−v₂) по знаку s.
   Ретроградность меняет геометрию сама — никаких эвристик по «быстрым»
   планетам; эвристика удалена.
3. В каждом аспекте: `orb_deg` (каноническое имя; `orb` оставлен как
   deprecated-алиас для существующих потребителей) и
   `speed_diff_deg_per_day` (v₁ − v₂, град/сутки).

**Живой прогон той же карты через MCP-инструмент**: 20 аспектов —
**5 applying / 15 separating** (было 20/20 true). Проверка знаков вручную:
Луна (+14.92°/д) трин Венере — сходится (applying), Солнце−Луна оппозиция
9.42° за точной — расходится (separating); обе в тестах.

**Тесты (WP-2+3).** Новый `backend/tests/test_natal_houses_aspects.py`
(9 тестов, через `AstrologyService.calculate_natal_chart` — тот самый
путь, который оборачивает MCP): все 10 эталонных положений; куспиды в
ответе; двунаправленная согласованность planet.house ↔ house.planets;
borderline-флаги (Плутон true/0.326°, Солнце false, правило
`borderline == (dist < 1°)` для всех); orb_deg+speed_diff в каждом
аспекте; `{True, False}` оба встречаются среди applying; знаки applying
для двух известных пар; без времени рождения — все null; скорости в
контракте (Луна ≈ +14.92, Уран < 0 и retrograde согласован).

**Критерии приёмки.** Выполнены: дома считаются в natal chart и связь
двунаправленная; borderline с расстоянием до куспида; applying по
скоростям обоих тел с полями orb_deg/speed_diff_deg_per_day; контрольная
карта 01.07.1977 22:30 Запорожье воспроизводит эталонную таблицу домов.

## WP-4 — HVdC-регрессия на живом тексте ✅ (кодировщик 3.1.0)

**Воспроизведение.** Оба отказа аудита воспроизведены дословно до правок:
«старший знакомый, с которым я иногда советуюсь, говорит, где нужно
копать» → знакомый = *indefinite* (male 0); «копаю землю … вижу: под
кустом лежат золотые монеты» → GF = 0 (RU и EN).

**Корневые причины и правки.**
1. **Субстантивированные прилагательные.** У «знакомый», «дежурный»,
   «больной» в OpenCorpora *вообще нет* NOUN-разбора (только ADJF) —
   правило «по тегам pymorphy» невозможно в принципе. Решение: курируемый
   список лемм (`substantivized_adjectives` в лексиконе: знакомый,
   незнакомый, старший, младший, прохожий, дежурный, больной, военный,
   ученый, взрослый, пожилой, молодой, покойный, любимый, родной), а РОД
   даёт морфология конкретной формы: знакомый → male, знакомая → female,
   знакомых (мн., род не размечен) → indefinite
   (`morphology.form_gender_for_lemmas`). «Прохожий»/«знакомый»/«знакомая»
   удалены из фиксированного indefinite-списка, который их затенял.
   Атрибутивный гейт: кандидат, за которым сразу стоит другой
   персонаж-токен, — прилагательное при нём, а не второй персонаж
   («старший знакомый» = один мужчина; «старший брат» = один «брат»).
2. **GF без глагола находки.** Все правила good fortune висели на глаголах
   «нашёл/обнаружил/откопал». Новое правило `valuable_discovery`:
   ценность (золот*, монет*, клад, сокровищ*, драгоценност*, бриллиант*,
   жемчуг*, слиток, самородок; en gold/treasure/coins/jewels/…) + глагол
   наличия/восприятия («лежат», «вижу», «оказывается», «блестит», "see",
   "lying", "turns out") в том же предложении → GF discovery. Гейты:
   отрицание любой части («не было золота», «не вижу монет»),
   родительный отрицания, «кладбищ*»/«кладк*» ≠ «клад» (хвостовой лимит
   корня + явные исключения), одно событие на предложение (перечисление
   «клад, монеты» и «нашёл клад: монеты лежат» не удваиваются).
   «Деньги» в ценности сознательно не включены (транзакционный шум).
3. Версия кодировщика 3.0.0 → **3.1.0** (видна в каждом ответе).

**Живой текст как эталон.** Все новые приёмочные тесты сформулированы на
дословных конструкциях из аудита владельца, не на тексте агента
(`test_hvdc_live_text.py`, с пометкой происхождения). Для полного
«монетного сна» оставлен skip-тест — ждёт дословный текст вместе со
слепой разметкой WP-17.

**Калибровка на корпусах норм 1966 (981 сон)** после правок: GF/сон
×1.80 (муж. корпус) / ×2.11 (жен.) против ×3.9 до прошлой сессии —
правило ценностей не раздуло перебор (кодировщики 1966 тоже считали
находку денег как GF; небольшой рост на жен. корпусе — легитимный
recall). male_percent 47.2/45.8 при нормах 67/48. Golden-set: все
пороги CI держатся (51 тест зелёный).
